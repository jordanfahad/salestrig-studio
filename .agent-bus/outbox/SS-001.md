### 4.1 Current providers

**Personal (`linkedin`).** Requests exactly `openid profile w_member_social`; uses `oneTimeToken=true`, `refreshWait=true`, maximum two activity executions through its worker, a normal editor and a 3,000-character limit (`libraries/nestjs-libraries/src/integrations/social/linkedin.provider.ts:29-48`; `libraries/nestjs-libraries/src/temporal/temporal.module.ts:21-39`). **Company Page (`linkedin-page`).** Extends the personal provider, requests `openid profile w_member_social r_basicprofile rw_organization_admin w_organization_social r_organization_social`, and uses a page-selection step (`libraries/nestjs-libraries/src/integrations/social/linkedin.page.provider.ts:19-38`). **Documentation nuance.** The current permissions catalog still lists `r_basicprofile` for approved Advertising/Community Management apps. OIDC `profile` supplies the authenticated member identity without it. A first comment is therefore a separate scheduled activity, not part of the LinkedIn post request.

**Retries / throttling.** `SocialAbstract.fetch` accepts only 200/201, retries HTTP 429, certain 500s, rate-limit strings and provider-classified retry responses with fixed 5-second sleeps. The retry counter permits four HTTP attempts total. It does not read `Retry-After` or use jitter; after exhaustion it throws non-retryable `BadBody`. HTTP 401 normally becomes non-retryable `RefreshToken` (`libraries/nestjs-libraries/src/integrations/social.abstract.ts:12-33`, `libraries/nestjs-libraries/src/integrations/social.abstract.ts:145-215`). LinkedIn classifies text including "resource is forbidden" as retryable, so a scope failure can be retried without benefit (`libraries/nestjs-libraries/src/integrations/social/linkedin.provider.ts:76-95`). Several auth/lookup/Page analytics calls use raw fetch and bypass this handling (endpoint tables).

Temporal activities allow three attempts with constant two-minute spacing and a ten-minute start-to-close timeout. Non-retryable typed failures take the workflow catch path; ordinary failures can also repeat within the five-iteration workflow loop (`apps/orchestrator/src/workflows/post-workflows/post.workflow.v1.0.5.ts:19-50`, `apps/orchestrator/src/workflows/post-workflows/post.workflow.v1.0.5.ts:164-267`). Queue concurrency is two per LinkedIn worker, not an application/member daily quota or a fleet-wide limiter (`libraries/nestjs-libraries/src/integrations/social/linkedin.provider.ts:43`; `libraries/nestjs-libraries/src/temporal/temporal.module.ts:21-39`). Official rate limits are per application and per member, and 429 can also represent protective throttling. [Rate limits](https://learn.microsoft.com/en-us/linkedin/shared/api-guide/concepts/rate-limits).

**Duplicate/partial-success gaps.** The remote write precedes durable release-ID persistence; retries are not keyed to a persisted publish attempt. `postSocial` also starts `streakWorkflow` before returning a successful provider response, so failure there can retry an already-created remote post (`apps/orchestrator/src/activities/post.activity.ts:228-268`; `apps/orchestrator/src/workflows/post-workflows/post.workflow.v1.0.5.ts:172-200`). A comment failure calls `changeState` on the main row even after the main post succeeded (`apps/orchestrator/src/workflows/post-workflows/post.workflow.v1.0.5.ts:219-260`). This is a credible duplicate-publication/false-error risk inferred from control flow, not a reproduced production incident.

**Scheduling gaps.** Database write and workflow start are not atomic, and start errors can be hidden. An hourly missing-post workflow attempts recovery via `signalWithStart`; the V105 `poke` handler only sets an otherwise-unused flag (`libraries/nestjs-libraries/src/database/prisma/posts/posts.service.ts:957-977`, `libraries/nestjs-libraries/src/database/prisma/posts/posts.service.ts:780-805`; `apps/orchestrator/src/workflows/missing.post.workflow.ts:13-17`; `apps/orchestrator/src/activities/post.activity.ts:73-105`; `apps/orchestrator/src/workflows/post-workflows/post.workflow.v1.0.5.ts:75-78`). The UI sends a UTC-formatted string without an offset, then the repository parses it with `dayjs(date).toDate()`; timezone/DST correctness needs tests under a non-UTC server (`apps/frontend/src/components/new-launch/manage.modal.tsx:390`; `libraries/nestjs-libraries/src/database/prisma/posts/posts.repository.ts:557`).

**Media gaps.** Videos ignore returned byte ranges, URLs after the first, and the returned upload token; this conflicts with the official upload instruction schema (`libraries/nestjs-libraries/src/integrations/social/linkedin.provider.ts:301-357`, `libraries/nestjs-libraries/src/integrations/social/linkedin.provider.ts:387-392`). The API defines inclusive ranges, one upload URL per instruction and ordered ETags passed with the returned session token. [Videos API](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/shares/videos-api?view=li-lms-2026-09). Twenty 30-second processing waits can consume the full activity timeout before upload/network overhead (`libraries/nestjs-libraries/src/integrations/social/linkedin.provider.ts:442-495`; `apps/orchestrator/src/workflows/post-workflows/post.workflow.v1.0.5.ts:19-27`). Personal image/document waits are heuristic. Image write-only access is documented; the code's equivalent blanket assertion for document GET access was **unverified** in the retrieved Documents documentation (`libraries/nestjs-libraries/src/integrations/social/linkedin.provider.ts:407-431`). [Images API](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/shares/images-api?view=li-lms-2026-09), [Documents API](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/shares/documents-api?view=li-lms-2026-09).

**Versions.** Ordinary post/media writes use 202601, while first comments use 202306 and several Page calls retain `/v2` (`libraries/nestjs-libraries/src/integrations/social/linkedin.provider.ts:727-734`, `libraries/nestjs-libraries/src/integrations/social/linkedin.provider.ts:760-770`; `libraries/nestjs-libraries/src/integrations/social/linkedin.page.provider.ts:295-346`). OAuth/OIDC `/v2` routes are separate; do not mechanically rewrite them. [Migration status](https://learn.microsoft.com/en-us/linkedin/marketing/integrations/migrations?view=li-lms-2026-09), [Versioning](https://learn.microsoft.com/en-us/linkedin/marketing/versioning?view=li-lms-2026-09).

### 4.3 Data model and token protection

- `Integration` holds provider/organization identity, access token, nullable refresh token and expiry, rootInternalId, and refreshNeeded/inBetweenSteps flags. - `Comments` is internal team feedback linked to a local user/post/organization, not LinkedIn comments. Its controller and repository only write the local row; no provider call occurs (`libraries/nestjs-libraries/src/database/prisma/schema.prisma:458-475`; `apps/backend/src/api/routes/posts.controller.ts:81-89`; `libraries/nestjs-libraries/src/database/prisma/posts/posts.repository.ts:883-896`). An inbound social inbox needs its own model.
- **The "existing encrypted integration storage" assumption is contradicted by this source path.** LinkedIn returns the raw OAuth access/refresh values, callback and service pass them through, and the repository writes them directly to `Integration.token/refreshToken` (`libraries/nestjs-libraries/src/integrations/social/linkedin.provider.ts:236-245`; `apps/backend/src/api/routes/no.auth.integrations.controller.ts:221-247`; `libraries/nestjs-libraries/src/database/prisma/integrations/integration.service.ts:125-142`; `libraries/nestjs-libraries/src/database/prisma/integrations/integration.repository.ts:243-295`). `PrismaService` is an ordinary client without an encryption extension in this file (`libraries/nestjs-libraries/src/database/prisma/prisma.service.ts:4-30`). Actual historical exposure is **unverified**.

### 4.5 Will not build

These are proposed product boundaries, following the task and `.agent-bus/PROJECT-THREAD.md:11`; they are not claims that every alternative is enabled today.

| Will not build | Closest permitted alternative |
|---|---|
| Scraping linkedin.com profiles, search results, feeds or comment HTML | Authorized Posts/Comments/Analytics APIs, limited to granted access; OIDC for the connected member. |
| Headless/browser-control LinkedIn actions, session-cookie reuse, private endpoints or extension-based LinkedIn automation | Official OAuth authorization and versioned API calls; manual user actions on LinkedIn when no supported API grant exists. |
| Automatic connection invitations, bulk outreach or drip DMs, even if a special partner API later becomes available | A human-owned reminder/draft and link to LinkedIn; official public posts or approved replies for engagement. There is no equivalent self-service outbound-DM/connection API alternative. |
| Automated profile visits or general lead harvesting | Consented OIDC identity, user-provided CRM records, and approved follower-only typeahead for mentions. |
| Circumventing 403/429 with alternate accounts, proxies, cookies or scraping fallbacks | Capability/reconnect messages, bounded retry with app/member budgets, and approved product access. |
| Selling an organic PDF as the native sponsored Carousel API | Clearly labeled document slideshow or organic multi-image post. |

Official APIs reduce unsupported automation, but no implementation can guarantee that an account will never be restricted. The promise should be official API/OAuth only, authorized actions, bounded traffic and transparent failures.
