## Goal

Fahad wants LinkedIn automation in Salestrig Studio for his clients: more of the LinkedIn work done by the product, built only on LinkedIn's official API so no client account is ever restricted. Before any code is written we need an accurate picture of what the code does today, what the official API allows with the scopes and products we have or can apply for, and a layered build plan. This task produces that plan. Claude reviews it with Fahad, then writes SS-002 to build the first slice.

## What to produce (in the handoff)

1. **Current state.** For each provider: scopes requested, every LinkedIn endpoint called (method, path, API version header), what each feature does (text post, image, video, document/carousel, multi-image, mentions, first comment, analytics, comments read/reply, token refresh). Include file and line references.
2. **Publishing path.** A short trace from "post scheduled in the UI" to "LinkedIn API call": controller, service, repository, Temporal workflow, activity, provider method. Note how failures, retries, 429 back-off and token expiry are handled today, and any gaps.
3. **Official API capability table** for these candidate features. For each: possible with current scopes / needs an additional scope / needs a restricted LinkedIn product (name it, e.g. Community Management API) / not possible via the official API.
   - Scheduled posts to personal profile and company pages (text, image, video, document, multi-image, poll)
   - First comment on our own post
   - Reading comments on our own posts and replying to them
   - Post analytics for personal profiles (impressions, reactions, comments)
   - Page analytics and follower statistics for company pages
   - @mentions of people and organisations in posts
   - Reposts / reshares
   - Connection requests, direct messages, profile viewing, people search
4. **Prohibited list.** Any candidate that needs scraping, headless control of linkedin.com, or automatic connection requests or messages: mark it "will not build" and propose the closest official-API alternative.
5. **Build plan, sliced.** Ordered slices, smallest valuable first. For each slice: files to change in each layer (provider, service, repository, controller, orchestrator workflow and activity, frontend component and SWR hook), Prisma schema changes with a migration plan that does not break existing users, new scopes and the fact that existing connected users must reconnect to grant them, tests to add (`*.salestrig.spec.ts`), and a rough size (S, M, L).
6. **Recommended SS-002**: the one slice to build first and why, written so Claude can turn it into a repo-mode spec.
7. **Risks and open questions** for Fahad, batched.
